# Dungeon Hunter: Design Document

Technical and visual design for the Dungeon Hunter MVP. The PRD (`docs/Dungeon Hunter MVP PRD.md`) says **what** we build; this document says **how** it is structured, so every plan under `docs/plans/` builds on the same names, boundaries, and rules.

When a plan and this document disagree, this document wins. Update it in the same commit as the change that diverges.

---

## 1. Design principles

1. **Gameplay first, backend last.** The run is fully playable offline by M4. The API is only a checkpoint service (load profile, end of run, purchase, auth).
2. **Logic is pure, rendering is Phaser.** Every rule that can be tested (damage, generation, payout, budgets, mods) lives in plain TypeScript with no Phaser import. Phaser objects call into it.
3. **Content is data.** Weapons, guardians, runners, mods, radio lines and logs are JSON validated by Zod. A new weapon is a JSON entry plus, at most, one new projectile behaviour.
4. **The server owns value.** The client reports what happened; the server decides Core Shards, prices and unlocks.
5. **Deterministic where it matters.** Layouts and loot come from a seeded RNG, split into independent streams, so a seed reproduces the same dungeon.
6. **Feel is a feature.** The combat-feel checklist is M1 scope, not polish.

### 2.2 Dependency rules

```
@dh/utils   <-  @dh/shared  <-  @dh/web (runtime)
                            <-  @dh/api (runtime)
@dh/api (types only, AppType) <- @dh/web (devDependency)
```

- `@dh/web` never imports `@supabase/supabase-js` and never sees a Supabase key.
- `apps/web/src/game/logic/**` never imports `phaser`, React, Zustand or TanStack. Enforced by an Oxlint `no-restricted-imports` override on that folder.
- `apps/web/src/game/**` never imports Zustand stores or TanStack Query. It talks to React only through the bridge (§4.3).
- `@dh/shared` contains no I/O. Rules there are pure functions both sides can call; only the API's result is authoritative.

### 2.3 Internal packages are consumed from source

`@dh/shared` and `@dh/utils` set `exports` to `./src/index.ts` (like `@dh/api` already does). Vite and Wrangler both compile TypeScript, so no `vp pack` step is needed during development. JSON is imported with import attributes: `import weapons from './data/weapons.json' with { type: 'json' }`.

## 4. Runtime architecture (web)

### 4.1 Who renders what

React owns every screen outside a run. Phaser owns the run, including HUD and Pause. They never render at the same time: when a run starts, React swaps the current screen for `<PhaserGame>`; when it ends, `<PhaserGame>` unmounts (destroying the game) and React shows Results.

```
AppRouter (Zustand `screen`)
 ├─ Title / Intro / Auth / StagingBay / Armory / Leaderboard / Settings / Results / Ending   (React)
 └─ Run  →  <PhaserGame runConfig=…/>                                                        (Phaser)
              Boot → Preload → Dungeon ⟂ Hud (parallel)  ⟂ Pause (launched on Esc)  → Lift (between sectors)
```

### 4.2 Phaser scenes

| Key       | Responsibility                                                                                 |
| --------- | ---------------------------------------------------------------------------------------------- |
| `boot`    | Disable context menu, read `RunConfig` from registry, start `preload`                          |
| `preload` | Load atlases, tilemaps, audio, bitmap font; progress bar; start `dungeon` + `hud`              |
| `dungeon` | World: tilemap, player, guardians, bullets, pickups, doors, camera, juice. Owns the `RunState` |
| `hud`     | Screen-space UI: bars, weapons, skill cooldown, Scrap, minimap, radio box, mod-pick overlay    |
| `pause`   | Resume, settings, abandon. Pauses `dungeon` (not `hud` timers that fade radio lines)           |
| `lift`    | Between sectors: heal 2 HP, pick 1 of 3 Vault Mods, descend                                    |
| `sandbox` | Dev only (`?scene=sandbox`): stress test, one room, spawn menu. Tree-shaken in production      |

Scene keys live in `game/scenes/keys.ts` as `SceneKey` constants.

### 4.3 React ↔ Phaser bridge

A single typed emitter in `game/bridge/bus.ts`:

```ts
export interface BridgeEvents {
  'run:ended': (summary: RunSummary) => void;   // Phaser → React (victory, death, or abandon)
  'settings:changed': (s: Settings) => void;    // Phaser pause menu → React store (persist)
}
export const bus: TypedEmitter<BridgeEvents>;
```

React → Phaser data goes in once, at construction: `new Phaser.Game(createGameConfig(host, runConfig))` stores `RunConfig` in `game.registry`. Rules: emit on meaningful events only, never per frame; no store or query calls inside `update()`.

```ts
interface RunConfig {
  runnerId: RunnerId;
  seed: string; // 8-char Crockford base32
  unlockedWeaponIds: WeaponId[]; // drop pool = starter pool ∪ these
  unlockedModIds: ModId[]; // mod pool = base pool ∪ these
  collectedLogIds: LogId[]; // so log rooms prefer uncollected logs
  settings: Settings;
  firstRun: boolean;
}
```

### 4.4 Game object model

Plain Phaser classes plus systems, no ECS library.

- **Entities** extend `Phaser.Physics.Arcade.Sprite` and hold a reference to a pure state object from `logic/` (e.g. `Player` holds `CombatantState`).
- **Systems** are classes constructed by `DungeonScene` and ticked from its `update(time, delta)` in a fixed order: `Input → Player → AimAssist → Weapons → Guardians/Bosses → Bullets → Pickups → Encounter → Juice → Minimap`.
- **All movement multiplies by `delta / 1000`.** Timers use scene time, never `Date.now()`.
- **Depth:** `sprite.setDepth(sprite.y)` each frame for actors; fixed depth bands for floor (0), decals (10), shadows (20), actors (y + 1000), bullets (5000), FX (6000).

### 4.5 Pooling and performance budget

| Pool                                | Max size           | Notes                                                 |
| ----------------------------------- | ------------------ | ----------------------------------------------------- |
| Player bullets                      | 512                | `physics.add.group({ classType, maxSize })` + `get()` |
| Enemy bullets                       | 768                | Bullet-hell phases of the Warden                      |
| Particles (sparks, casings, muzzle) | 3 emitters, reused | `explode()` only, no per-shot emitters                |
| Damage numbers                      | 64                 | Only when setting enabled                             |
| Pickups (orbs, scrap)               | 128                |                                                       |

Targets from the PRD: 300 bullets on screen at 60 fps on a mid-range laptop; first load under 5 s. `sandbox` has a 300-bullet stress button and an FPS readout.

### 4.6 Input

`systems/InputSystem.ts` exposes an abstract `InputState` read once per frame so gameplay never touches devices directly:

```ts
interface InputState {
  move: { x: number; y: number }; // normalized, length ≤ 1
  aimWorld: { x: number; y: number };
  fire: boolean;
  skill: boolean;
  dash: boolean; // dash/skill are edge-triggered (pressed this frame)
  swap: boolean;
  interact: boolean;
  pause: boolean;
  map: boolean;
  device: "kbm" | "pad";
}
```

Bindings (fixed, no remapping in MVP): WASD, mouse aim, LMB fire, RMB/Space skill, Shift dash, Q/wheel swap, E interact, Esc pause, Tab map. Gamepad: left stick move, right stick aim (aim point = player + stick × 96 px), RT fire, LT skill, A dash, Y swap, X interact, Start pause.

## 5. Pure game logic (`apps/web/src/game/logic`)

| Module                | Key exports                                                                     |
| --------------------- | ------------------------------------------------------------------------------- |
| `combat/combatant.ts` | `applyDamage(state, amount, now) → DamageResult`, `tickShieldRegen(state, now)` |
| `combat/stats.ts`     | `deriveStats(base, mods) → PlayerStats`                                         |
| `combat/aim.ts`       | `assistAngle(origin, cursor, targets, mode, prevAngle) → number`                |
| `dungeon/generate.ts` | `generateSector(seed, sector, opts) → DungeonLayout`                            |
| `dungeon/validate.ts` | `isReachable(layout)`, `validateLayout(layout) → string[]`                      |
| `encounter/budget.ts` | `roomBudget(sector, roomsCleared)`, `buildWaves(budget, pool, rng) → Wave[]`    |
| `run/runState.ts`     | `createRunState(config)`, reducers for room cleared, boss killed, pickups       |
| `run/summary.ts`      | `toRunResult(state) → RunResult`                                                |
| `loot/tables.ts`      | `rollChest(rng, pool, luck)`, `rollModChoices(rng, pool, owned, n=3)`           |
| `mods/apply.ts`       | `applyMod(stats, mod)`, hook dispatch (`onBossKilled`, `onContact`)             |

Tests sit next to each module as `*.test.ts` and run with `vp test`.

### 5.1 Seeded RNG (`@dh/utils/rng.ts`)

- Hash: `cyrb128(seed)` → four 32-bit words; generator: `sfc32`.
- `createRng(seed: string): Rng` with `next() ∈ [0,1)`, `int(min, maxInclusive)`, `pick(arr)`, `weighted(entries)`, `shuffle(arr)`, `chance(p)`, `fork(label: string): Rng`.
- Streams: `rng.fork('layout:s1')`, `fork('loot:s1')`, `fork('spawns:s1:r4')`. Combat randomness (spread, pitch) uses `Math.random()`; it does not need to be reproducible.
- Seed format: 8 chars from Crockford base32 (`0-9A-HJKMNP-TV-Z`), generated by `generateSeed()`. Dev builds accept `?seed=` overrides.

## 6. Content data (`@dh/shared/src/data`)

IDs are kebab-case strings. Each ID set is an `as const` tuple in `schemas/ids.ts` (`WEAPON_IDS`, …) feeding `z.enum`, so `WeaponId`, `GuardianId`, `ModId`, `RunnerId`, `LogId`, `BossId` are literal unions; a test asserts each JSON file's IDs equal its tuple. Every JSON file is parsed through its Zod schema in a test so a bad edit fails CI.

| File             | Schema               | Key fields                                                                                                                                              |
| ---------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `runners.json`   | `RunnerSchema`       | id, name, title, hp, shield, energy, skill { id, cooldownSec, durationSec }, unlockCost                                                                 |
| `weapons.json`   | `WeaponSchema`       | id, name, type, rarity, energyPerShot, damage, fireRate, spreadDeg, projectileSpeed, pellets, behaviour, behaviourParams, shake, knockback, sfx, sprite |
| `guardians.json` | `GuardianSchema`     | id, name, sectorMin, hp, speed, contactDamage, budgetCost, ai, attack {…}, scrap, energyOrbChance                                                       |
| `bosses.json`    | `BossSchema`         | id, name, sector, hp, phases[] { id, untilHpPct, patterns[] }, params { tunable attack numbers }                                                        |
| `sectors.json`   | `SectorConfigSchema` | id, name, tileset, accent, music, bleedLevel, radioEnterBeat                                                                                            |
| `mods.json`      | `ModSchema`          | id, name, description, inBasePool, effects: ModEffect[] (§6.2)                                                                                          |
| `radio.json`     | `RadioLineSchema`    | id, beat, speaker ('ops'│'vigil'), text, durationMs                                                                                                     |
| `logs.json`      | `VaultLogSchema`     | id, sector, title, lines[2..4]                                                                                                                          |
| `armory.json`    | `ArmoryItemSchema`   | itemType ('runner'│'weapon'│'mod'), itemId, cost                                                                                                        |

### 6.1 Projectile behaviours

`behaviour` is one of: `bullet`, `pierce`, `bounce`, `explosive`, `chain`, `beam`, `charge-orb`, `melee-swing`, `burst` (fires `behaviourParams.count` bullets with `interval`). Each maps to one class in `game/systems/weapons/behaviours/`. This is the only code a new weapon may add.

### 6.2 Mod effects

```ts
type ModEffect =
  | {
      kind: "stat";
      stat:
        | "fireRateMul"
        | "damageMul"
        | "maxShield"
        | "maxEnergy"
        | "maxHp"
        | "pickupRadiusMul"
        | "dashCharges"
        | "chestLuck";
      value: number;
    }
  | { kind: "flag"; flag: "bulletsBounce" | "thornContact" }
  | { kind: "hook"; hook: "onBossKilled"; action: "heal"; value: number };
// A mod carries `effects: ModEffect[]`; Overclock Core = [damageMul 1.25, maxHp -1].
```

Stat effects compose: multipliers multiply, flat values add. `maxHp` never drops below 1.

## 7. Gameplay rules (canonical numbers)

Values from the PRD are starting values; tuning changes JSON, not code.

### 7.1 Resources and damage

- Order: Shield absorbs first, then HP. Enemy hits deal integer damage (default 1).
- Shield regen: +1 per second after **3 s** without taking damage.
- Post-hit invulnerability: **0.5 s**. Dash: **0.2 s** i-frames, 0.6 s cooldown, 1 charge (+1 per Dash Coil), dash distance 48 px.
- Energy: spent per shot (`energyPerShot`) or per second for beams. Starter pistol and melee cost 0. A weapon with insufficient energy dry-fires (click SFX, no shot).
- Runner skills: Vex **Overcharge** (×2 fire rate, 0 energy cost, 5 s, cooldown 20 s); Kit **Patch Drone** (turret auto-fires 8 s, cooldown 22 s).
- Enemy hit: white flash 50 ms (`setTint(0xffffff).setTintMode(Phaser.TintModes.FILL)`), knockback from weapon data. Stun (Shock Baton): 0.5 s.
- Elite: ×1.5 scale, ×2 HP, guaranteed energy orb, max 1 per room.
- Bleed variant: ×1.4 HP, ×1.25 bullet speed, magenta tint, death puddle (1 dmg, 2 s).

### 7.2 Aim

- `soft` (default): if a visible enemy lies within 24 px of the cursor, bend the aim toward the one closest to the cursor, clamped to 8°.
- `full`: aim at the nearest visible enemy within 160 px; fall back to cursor.

### 7.3 Dungeon

- 5×5 grid, Start at (2,2). Rooms are 15×11 tiles of 16 px (240×176 px). Corridors are 3 tiles wide and 4 tiles long, so the grid pitch is 19×15 tiles.
- Doors sit at the centre of each edge (N/S at column 7, E/W at row 5), 3 tiles wide.
- Rooms per sector: 7 to 9. Start 1, Combat 4–6, Chest 1, Vendor 1 (sectors 2–3), Log 0–1, Boss 1.
- Boss = farthest by path length, ≥ 4 rooms from Start, exactly one connection (dead end). Chest and Vendor never adjacent to Start.
- Reachability check on every layout; up to 50 regeneration attempts with `fork('layout:sN:attemptK')`, then throw (a test guarantees 1000 seeds never throw).
- Difficulty budget per combat room = `SECTOR_BASE[s] + roomsClearedThisRun`, with `SECTOR_BASE = { 1: 4, 2: 8, 3: 12 }`. Waves: 2 waves, 3 when budget ≥ 10. Costs live in `guardians.json` (`budgetCost`).
- Lift is not a grid room. Killing a sector boss spawns a lift pad in the arena; using it starts the `lift` scene.

### 7.4 Economy

- Scrap: from guardians (`scrap`), crates (1–3) and room clears (3 + sector). Resets each run.
- Core Shards (server formula, `@dh/shared/rules/payout.ts`):
  `2 × roomsCleared + 25 × sectorBossesKilled + (victory ? 100 : 0)`, where `roomsCleared` counts combat rooms only and `sectorBossesKilled = min(bossesKilled, 2)`.
- Run validation (`@dh/shared/rules/validateRun.ts`), all reject with a reason code:
  - `roomsCleared ≤ 6 × sectorReached` (`MAX_COMBAT_ROOMS_PER_SECTOR = 6`)
  - `bossesKilled ≤ sectorReached`; `victory ⇒ sectorReached = 3 ∧ bossesKilled = 3`
  - `durationSec ≥ 8 × roomsCleared`; `victory ⇒ durationSec ≥ 360`
  - `logsFound` ⊆ known log IDs of sectors ≤ `sectorReached`
  - Server only: 1 accepted submission per 60 s per account.
- Armory prices (`armory.json`): Kit 300, each Rare weapon 80, each Epic 150, Thorn Plating / Lucky Seal / Dash Coil 60 each.

## 8. Profile and persistence

### 8.1 One interface, two backends

```ts
interface ProfileRepository {
  load(): Promise<Profile>;
  submitRun(result: RunResult): Promise<RunReward>; // { shardsAwarded, newLogIds, profile }
  purchase(item: ArmoryItemRef): Promise<Profile>;
  loadSettings(): Promise<Settings>; // settings travel with the profile's backend
  saveSettings(settings: Settings): Promise<void>;
  markSeen(flag: "intro" | "ending"): Promise<Profile>; // per-device flags, stay local for accounts
}
```

- `submitRun` resolves to `RunReward = { shardsAwarded, newLogIds, rejected?, profile }`.
- `LocalProfileRepository` (guest, M5): `localStorage['dh.profile.v1']`, computes payout with the same shared rules.
- `ApiProfileRepository` (account, M6): calls the Hono RPC client.
- TanStack Query hooks (`useProfile`, `useSubmitRun`, `usePurchase`) depend only on the interface. The run is submitted from the `run:ended` handler in `AppRouter` (once per run, keyed by seed + duration + kills), not from a Results effect. The active repository is chosen by session state.
- Every persisted blob has `version`; `migrateLocalProfile(raw) → Profile` upgrades or resets.

### 8.2 Client state (Zustand)

- `useSettingsStore`: `Settings` (persisted to localStorage for guests, mirrored to API for accounts).
- `useSessionStore`: `screen`, `selectedRunnerId`, `lastRunSummary`, `authMode: 'guest' | 'account'`.

```ts
interface Settings {
  version: 1;
  musicVolume: number; // 0..1
  sfxVolume: number; // 0..1
  aimMode: "soft" | "full";
  screenShake: number; // 0..1 multiplier, 0 disables
  damageNumbers: boolean; // default false
}
```

## 9. API design (`apps/api`)

### 9.1 Endpoints

| Method | Path                   | Auth    | Body (Zod)             | Response                                |
| ------ | ---------------------- | ------- | ---------------------- | --------------------------------------- |
| GET    | `/api/health`          | none    |                        | `{ ok: true }`                          |
| POST   | `/api/auth/register`   | none    | `RegisterSchema`       | `MeResponse` + cookies                  |
| POST   | `/api/auth/login`      | none    | `LoginSchema`          | `MeResponse` + cookies                  |
| POST   | `/api/auth/logout`     | session |                        | `204`, cookies cleared                  |
| GET    | `/api/me`              | session |                        | `MeResponse`                            |
| PUT    | `/api/me/settings`     | session | `SettingsSchema`       | `204` (additive to PRD: `saves` slot 0) |
| POST   | `/api/me/import`       | session | `GuestImportSchema`    | `MeResponse` (once per account)         |
| POST   | `/api/runs`            | session | `RunResultSchema`      | `RunReward` or `422 { code }` / `429`   |
| POST   | `/api/armory/purchase` | session | `ArmoryItemRefSchema`  | `MeResponse` or `409 { code }`          |
| GET    | `/api/leaderboard`     | none    | query `period`, `kind` | `LeaderboardResponse`                   |

All request/response schemas live in `@dh/shared/schemas/api.ts`. `export type AppType` from `apps/api/src/index.ts` drives the Hono RPC client.

### 9.2 Auth and session

- Register: `auth.admin.createUser({ email, password, email_confirm: true })`, insert `profiles` row (username unique), then sign in. (No email verification in the MVP: an address is not proven to belong to the player. Revisit before adding password reset or anything sent by email.)
- Logout revokes the session server-side (`auth.admin.signOut(accessToken, "local")`) before clearing cookies.
- Login: `auth.signInWithPassword`. Store access token in `dh_at` and refresh token in `dh_rt`, both `HttpOnly; Secure; SameSite=Lax; Path=/api`.
- `sessionMiddleware`: verify access token; on expiry refresh with `dh_rt` and rewrite cookies; sets `c.var.userId`. Never read a user id from a body.
- One Supabase client per request, created with `SUPABASE_SECRET_KEY` (bypasses RLS); sign-in and refresh each use a fresh client so no session leaks between calls. Access tokens are verified with `auth.getClaims(token)`.
- Emails are trimmed and lowercased by `RegisterSchema` / `LoginSchema`. A taken username deletes the just-created auth user (no orphans).
- The project runs against Supabase cloud (no local Docker stack). `db.types.ts` is not generated yet: the repo maps rows by hand in `db/supabaseRepo.ts`; run `vp run db:types` after linking if typed queries are wanted.

### 9.3 Error format

`{ error: { code: string, message: string } }` with stable codes: `VALIDATION`, `UNAUTHORIZED`, `USERNAME_TAKEN`, `EMAIL_TAKEN`, `INVALID_CREDENTIALS`, `RUN_REJECTED:<reason>`, `RATE_LIMITED`, `INSUFFICIENT_SHARDS`, `ALREADY_OWNED`, `UNKNOWN_ITEM`, `IMPORT_USED`.

### 9.4 Data model

As in SETUP.md §6, plus:

- `profiles.imported_guest boolean not null default false`
- `runs` index on `(profile_id, created_at desc)` for rate limiting
- SQL functions (`supabase/migrations/*_gameplay.sql`), each one call under a `for update` lock on the profile row: `award_run` (60 s rate limit, run row, new logs, shards), `purchase_unlock`, `import_guest`; plus `profile_stats` and `leaderboard(period, kind, limit)` (one best row per profile, weekly = since Monday 00:00 UTC). They raise their error code as the exception message; `db/supabaseRepo.ts` maps it.
- `profiles.imported_runs`, `imported_victories`, `imported_best_victory_sec`: guest import keeps max(guest, account) counts without inventing run rows.
- RLS enabled on every table with zero policies. The `anon`/`authenticated` roles get no grants beyond defaults.

## 11. Visual design system

### 11.1 Rendering

- Internal resolution **480×270**, `pixelArt: true`, `Phaser.Scale.FIT`, centred. Integer scaling preferred: the host element snaps to the largest integer multiple that fits; letterbox colour `void`.
- Camera `roundPixels: true` (Phaser 4 defaults to `false`; set explicitly). Actors use `vertexRoundMode: 'safeAuto'`.
- Sizes: tiles 16×16; Runners 16×24; guardians 16×16 to 32×32; bosses drawn at the texture sizes their hitboxes were tuned on in plans 14–20 (Gatekeeper and Core Warden 64×64 shown at 0.75, Hydra core 32×32, heads 16×16, Warden arms 10×10).
- Runner and boss art is generated by `apps/web/scripts/gen-art.ts` into `public/assets/sprites/{runners,bosses}.{png,json}` (Phaser json-array atlases, frames `<id>/<anim>/<i>`). `content/animations.ts` builds `runner.<id>.<anim>` / `boss.<id>.<anim>` from the frame names; a missing atlas or animation falls back to the placeholder with one warning. Replacing the art means replacing those two atlases, no code change.
- No Soul Knight sprites, names, or recognisable designs. Prototype art from licence-checked free packs (record each in `apps/web/public/assets/CREDITS.md`).

### 11.3 Typography

- One pixel font for React and Phaser: **Silkscreen** (OFL 1.1, `public/assets/fonts/ui.woff2`, recorded in CREDITS.md).
- Phaser: canvas Text with the same web font (`load.font`), rendered at 4× resolution, sizes 8 and 16 internal px only (`hud/text.ts` `UI_FONT`). Silkscreen is a true 8 px pixel font, so this stays crisp; BitmapText remains the fallback if blur ever shows.
- React: `@font-face` with `font-smooth: never; -webkit-font-smoothing: none`; sizes 16 / 24 / 32 / 48 CSS px (multiples of 8).

### 11.4 React UI language

- Panels: `ink` fill, 2 px `steel-700` border, 2 px inner `steel-900` bevel. Square corners, no blur, no soft shadows.
- Buttons: `PixelButton` with states default / hover (`amber-500` border) / focus (2 px `bone` outline, always visible) / pressed (1 px down) / disabled (`steel-600` text).
- Every screen is fully keyboard-navigable (arrow keys + Enter/Esc) and works with a gamepad D-pad in menus where cheap.
- Art inside React uses `image-rendering: pixelated` and integer scale.
- Layout: centred 960×540 stage scaled by integer factor; content never depends on viewport width beyond that.

## 12. Narrative system

- Beats (`radio.json` `beat` field): `intro`, `s1-enter`, `gatekeeper-dead`, `s2-enter`, `hydra-dead`, `s3-enter`, `core-chamber`, `victory`, `death`, `vigil-sealed`.
- `systems/NarrativeDirector.ts` maps dungeon events to beats (`logic/story/beats.ts`, each beat once per run via a `BeatLog` kept in the game registry) and emits `radio:say` / `vigil:banner` / `radio:flush` on the dungeon scene's events; the HUD draws them, so text never pauses combat. The sector-enter beat waits for the 400 ms camera fade-in. Ops lines in Sector 3 pass through `degradeText(…, 2)`; VIGIL lines after `hydra-dead` jitter.
- VIGIL warnings ("INTRUDER. SECTOR SEALED.") use a separate glitch-styled banner at top-centre for 1.5 s on the first door lock of a sector, then a 0.6 s `SEALED.` flash.
- Vault Logs: 9 entries, 3 per sector. A log room, when generated, offers one uncollected log of that sector (falls back to a collected one). Logs found are part of `RunResult.logsFound` and saved to the profile.
- Intro cards (4) and ending cards are React screens (`cards.json`, `CardSchema`); intro shows on first launch, skippable; ending shows on first victory.

## 13. Security

- Secret key only in `apps/api/.dev.vars` (gitignored) and Wrangler secrets. Never `VITE_`-prefixed.
- CORS: `WEB_ORIGIN` only, `credentials: true`. Production serves `/api/*` on the same site as the web app.
- Zod validates every body and query. Unknown keys are stripped.
- Anti-cheat is the rule set in §7.4. It stops casual devtools cheating, not determined attackers; that is accepted for the MVP.
- Guest import caps: shards capped (not rejected) at 1000, unknown unlocks and logs dropped silently, once per account.
- The web keeps a finished run in `sessionStorage` (`profile/pendingRun.ts`) until the server accepts or rejects it, and resubmits it once after the next login.

## 14. Naming and code conventions

- Files: `PascalCase.ts` for classes (entities, scenes, systems), `camelCase.ts` for modules of functions, `*.test.ts` beside the code.
- IDs: kebab-case in data; TypeScript unions inferred from data.
- Events: `domain:verb` (`run:ended`, `room:cleared`).
- No `any` (lint error). No default exports except Phaser scene classes are named exports too.
- Comment the why, not the what.
